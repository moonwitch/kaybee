templates / v0.1 · for backend & Penpot wireframes

Doc templates & component primitives.

Frame-style references for the three content surfaces you'll be modelling in the backend: the SOP template, the generic document template, and the comments thread. Each frame uses the Loop Library tokens (Geist + Monokai Pro Sun) and is annotated with the data fields it expects, so you can paste into Penpot and design the schema against it.

1. Section heading

A short framing paragraph explains the section's intent before the steps.

  1. Step title — verb + object
    One- or two-sentence body. Include the exact command, file path, or URL.
    role · ic
  2. Decision point — branching
    If <condition> → continue at step N. Else escalate to on-call.
    role · ic / oncall
  3. Verification step
    How to confirm success: a metric, a dashboard, a customer-facing signal.
    role · ic

A Required header fields
Every SOP must have a category, title, owner, severity, and reviewed-date.
fields → category, title, owner, severity, lastReviewedAt
B Steps are first-class
Each step has a title, body, and a role assignment. Order is preserved as index.
type → steps: Step[] · Step { id, title, body, role }
C Callouts are typed
Warning, success, danger, info — the colour is computed from kind, not authored per-instance.
enum → warning | success | danger | info
D Review cadence
The library badges any SOP with lastReviewedAt > 90d as stale on the home page.
computed → isStale = now − lastReviewedAt > 90d

A One renderer, many types
Manuals, RFCs, memos all share this template; type drives the tag colour and any type-specific badges.
discriminator → type ∈ {manual, rfc, memo, checklist}
B Block tree storage
Body is stored as an ordered tree of blocks: heading, paragraph, list, image, code, callout, quote, divider.
body → Block[] · jsonb
C TOC is derived
The right-rail TOC is built from heading blocks at depth ≤ 3. Don't store separately.
computed → toc(body)
D Verification badge
verified is set when an owner re-attests within 90 days; otherwise stale; unverified for new docs.
enum → verified | stale | unverified

A Anchored to a block
Every thread points at a single block id in the parent doc. If the block is deleted in Docs, the thread becomes orphaned and shows in the side panel only.
fields → docId, blockId, anchorRange?
B Three states
open, resolved, orphaned. Resolved threads collapse but are never deleted.
enum → open | resolved | orphaned
C Two kinds of comment
Plain comment lives in Loop only. suggestion mirrors a Google Docs suggestion and round-trips through the sync.
enum → comment | suggestion
D Reactions are first-class
Stored as a {emoji, userId[]} map per comment — not as nested comments. Lets us deduplicate the "+1" noise that Google Docs generates.
reactions → Record<emoji, userId[]>
E Realtime
Thread updates are pushed over the same channel the doc body uses, so the reader sees new comments without polling.
channel → doc:{docId}
