Lifecycle

What happens when a Looper edits a Google Doc

T+0s
Edit lands in Google Docs.

An author saves a change to /Loop Library/ops/sev1-runbook. Drive fires a changes.watch notification on our registered channel within ~1 second.

T+1s
Webhook receiver ACKs and enqueues.

The receiver verifies the channel token, drops the resourceId on a Pub/Sub topic keyed by docId, and returns 200 to Drive in under 50ms. We never hold the request open.

T+2s
Transformer pulls the new revision.

Worker calls docs.get + drive.revisions.get, dedups against the last stored revision, and converts the structured content tree into Loop's block schema. Suggestions and comments stay attached.

T+3s
Assets re-hosted in parallel.

Inline images are fetched with the service-account token, hashed, written to the CDN at /a/<sha256>, and the URLs in the stored blocks are rewritten. Old asset rows are GC'd after 7 days.

T+4s
Doc store + search index update atomically.

One transaction writes the new block tree, the revision pointer, and bumps the search index. Anyone with the library open sees a soft toast: Updated by Jordan · 2s ago.

∞
Reconciler keeps us honest.

Every 5 minutes a sweep lists the folder via drive.files.list and reconciles anything the push channel may have dropped — including out-of-band moves, deletions, and ACL changes.

Going the other way

Library edits → Google Docs

A small in-place editor in the Library produces a minimal block-level diff. The outbound writer translates that into a docs.batchUpdate request — typically a handful of InsertTextRequest, DeleteContentRangeRequest, or UpdateTextStyleRequest operations.

Before writing, we re-fetch the current revision id. If it has moved since the user started editing, we run a 3-way merge on block boundaries. Conflicts that can't be merged are surfaced inline as a Google Docs suggestion attributed to the original author — never silently overwritten.

Writes go through the same service account, so they show up in Drive's audit log as via Loop Library, attributed to the editing user via actAs impersonation.

The interesting bits

Why assets are their own pipeline

1 Original urls are short-lived

Drive serves inline images under signed, scoped, expiring URLs. We can't link to them directly — they'd break the moment a reader's session lapses. So every image is mirrored to our CDN on first sight.

avg pull · 180ms · 92% cache hit on second sync

2 Content-addressed = free dedup

Assets are stored by SHA-256 of their bytes. The same logo pasted into 40 different runbooks costs us one upload and one CDN entry — and the URL never changes between syncs.

312 docs · 4,891 image references · 1,204 unique blobs

3 ACL-aware delivery

For docs that aren't org-wide-readable we sign the CDN URL with a short-TTL token derived from the viewer's GWS identity. Public docs get plain immutable URLs; protected docs get token-protected ones, transparently.

14 of 312 docs are restricted · token TTL 5min · auto-renew
